# Batched inference dropped records from rate-limited sources (FIXED)

Reproduced on this machine with `verify_batch_delivery.test` (Generator source, in this directory)
and two variants generated by `gen_delivery_controls.py` (File and TCP sources).

Each run compares three independent counters, all of which agree in every configuration:

* the `Checksum` sink's tuple count,
* the operator's own per-record counter (`cache hits=..., misses=...` in the run log, incremented
  inside the scan loop, never reading buffer metadata),
* a control section running the same source with no inference operator at all.

## Result: delivered / expected

| source | batch 1 | batch 8 | batch 64 | batch 512 | batch 2048 |
|---|---|---|---|---|---|
| File, 20k rows (1 buffer)      | 100% | 100%   | 100%  | 100%  | 100% |
| File, 200k rows (~6 buffers)   | 100% | -      | 100%  | 100%  | -    |
| TCP, `MOCK_TUPLE_RATE=50000`   | 100% | 99.95% | 99.3% | 95.3% | -    |
| Generator, `emit_rate 50000`   | 100% | 99.6%  | 94.0% | 51.7% | 13.1% |

Generator, full sweep at 100000 records: batch 1/2/4 lose nothing; 8 -> 99600, 16 -> 98800,
32 -> 97200, 64 -> 94032, 128 -> 87760, 256 -> 75472, 512 -> 51680, 1024 -> 25928, 2048 -> 13052.

## Buffer fill level is the driver

TCP source, batch 512, 60000 rows - delivery improves monotonically as the offered rate (and hence
how full each buffer is) rises, with a residue smaller than one batch:

| `MOCK_TUPLE_RATE` | delivered | lost |
|---|---|---|
| 10000/s   | 45784 (76.3%) | 14216 |
| 50000/s   | 57284 (95.5%) | 2716 |
| 200000/s  | 59030 (98.4%) | 970 |
| 1000000/s | 59561 (99.3%) | 439 (< one batch of 512) |

Generator source, 100000 records, same test with only the emit rate changed:

| generator rate | batch 64 | batch 512 |
|---|---|---|
| `emit_rate 50000` (partial buffers, ~500 tuples/buffer) | 94032 | 51680 |
| unbounded (buffer-limited, i.e. full buffers)           | 99939 | 99939 |

61 tuples lost in the full-buffer case, identical at both batch sizes: an end-of-stream tail.

**Rule of thumb: roughly one partial batch is lost per buffer close.** The loss fraction is about
`(tuples_per_buffer mod batch) / tuples_per_buffer`, which is negligible when buffers are full and
severe when a slow source emits small buffers. For a rate-limited source
`tuples_per_buffer ~ rate x flush_interval`, so the damage is worst at exactly the low-rate,
large-batch corner.

## What is established

* Loss is **deterministic**: identical counts *and* identical checksums at 1, 2, 4 and 16 worker
  threads, and across the IREE and OpenVINO backends. It is not a data race.
* Loss is **zero at batch size 1** (no batching operator in the plan) and grows with batch size.
* The source is not at fault: the no-inference control returns 100% from the same source.
* It scales with how *partially filled* the input buffers are. A File source fills its buffers and
  loses nothing; a rate-limited source emits small buffers (Generator: `rate x flush_interval`,
  ~500 tuples at 50000/s and 10 ms) and loses heavily.

## Root cause and fix

`BatchInferenceOperatorHandler::getOrCreateNewBatch()` decided whether the current batch could still
accept records with

    batches.back()->state == BatchState::MARKED_AS_EMITTED

A batch leaves `MARKED_AS_CREATED` in two steps: `emitBatchesToProbe` sets `MARKED_AS_EMITTED`, then
the inference operator scans it and `markBatchProcessed` sets `MARKED_AS_PROCESSED`. The guard only
recognised the middle state, so whenever the probe finished scanning a batch *before* the next input
buffer arrived, the batch was already `PROCESSED`, the guard missed it, and every record that
followed was appended to a batch nobody would read again.

That is why a File source looked clean (buffers arrive back-to-back, so the batch is usually still
`EMITTED` when the next records land and the guard happens to fire) while a rate-limited source lost
heavily: the gap between two buffers is exactly the window in which the probe completes. It also
explains the deterministic arithmetic progression - with 500-tuple buffers and batch 512, the 12
records arriving after the emit but before `tuplesSeen` reached 512 were lost, and the following
batch was then cut 12 records early, and so on.

The fix rejects any state other than `MARKED_AS_CREATED`:

    if (batches.empty() || tuplesSeen == batchSize || batches.back()->state != BatchState::MARKED_AS_CREATED)

### Verified after the fix

| case | before | after |
|---|---|---|
| Generator, batch 8 / 64 / 512 / 2048 | 99.6% / 94.0% / 51.7% / 13.1% | 100% at all |
| TCP 10k/s / 50k/s / 200k/s, batch 512 | 76.3% / 95.5% / 98.4% | 100% at all |
| File, 200000 rows, batch 512 | 100% | 100% (no regression) |

Full sweep after the fix, Generator at 100000 records, 4 threads: batch 1, 8, 16, 64, 128, 512,
1024 and 2048 all deliver exactly 100000.

### Regression check

The whole `nes-systests/inference` suite was run before and after, at the default batch size and at
batch 64, with identical results. Two pre-existing failures are unrelated to this bug and unchanged
by the fix:

* `InferModelCache.test` at batch 64: 16 of 32 queries fail. The test's matrix is
  `prediction_cache_scope: [THREAD_LOCAL, GLOBAL]`, and `LowerToPhysicalInferModel` deliberately
  throws `UnsupportedQuery` for a GLOBAL cache with batched inference. The 16 GLOBAL variants are
  the ones that fail, by design.
* `InferModelBackend.test`: 1 of 3 queries fails at every batch size, before and after.

## Original lead on the mechanism (superseded by the root cause above)

The arithmetic is consistent with **the last batch emitted at each buffer close being dropped**
roughly half the time. With 100000 records at 50000/s and a 10 ms flush there are ~200 buffers of
~500 tuples:

* batch 8: each close emits 62 full batches + one 4-tuple remainder; losing that remainder about
  half the time gives ~2 tuples/buffer -> 400 lost. Observed: 400.
* batch 512: each close emits exactly one batch of ~500 (the batch never fills); losing it about
  half the time gives ~48% loss. Observed: 48.3%.

`BatchingPhysicalOperator::close` -> `emitBatchesProxy` emits one chunk per created batch, numbered
`INITIAL_CHUNK_NUMBER + index` with `lastChunk = (index + 1 == size)`, using the *input buffer's*
sequence number. `getCreatedBatches()` returns all globally-created batches, so a buffer close that
completes no new batch emits no chunk at all for its sequence number. Both the last-chunk handling
and the possibility of a sequence number with zero chunks are worth checking first.

## Consequence for the adaptive-optimizer experiment

The experiment's rate axis needs a rate-limited source, and both rate-limited sources lose records
once batching is on. Until this is resolved, the batching and deduplication arms (4 of the 7 in
Phase 1, and all of Phase 2) measure a truncated workload and are not comparable with batch-1 runs.
The baseline, cache and precision arms at batch 1 are unaffected - the Phase 0 numbers for those
are sound.
